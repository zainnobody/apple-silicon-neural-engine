## 2. What is known about the M3 (H15) ANE

| Topic | Known | Tag / source |
|---|---|---|
| Generations | ANE guide decodes 28 compiler targets A11 to A18, M1 to M5, maps each M part to an H-series id. Measured silicon in that paper: M1 and M5 only. Core counts 4 (M1) to 16 (M5). | [V] https://arxiv.org/abs/2606.22283 (Bryngelson, v2 dated 2026-10-16); https://ane-guide.readthedocs.io/ |
| Firmware | ANE has an internal CPU running **unencrypted firmware**, 93-command host protocol, ~130 us firmware round trip per dispatch. | [V] https://arxiv.org/html/2606.22283 (intro, ch. 29-30). Body chapters were truncated in fetch. |
| DART | Dedicated chapter on ANE DART address space, two-stage translation, "host-to-firmware rebase". M1 driver uses dart0/1/2 regions and copies TTBR from dart0 to dart1/2. | [V] arXiv html; eiln ane_drv.c |
| Power domains | M1: multiple `power-domains` phandles via genpd. M2 path: 8 domains, must be raised in order (sys_mpm, td, base, set1..4, ane_cpu). | [V] eiln ane_drv.c; ane_t6021.h |
| Generation split | M1 (H13): no firmware load, driver drives tile manager directly. M2 (H14): firmware-based, boot sequence via ASC. [I] M3 (H15) is almost certainly firmware-based like M2, since M4 is, per the guide. The guide does not state H15 specifics in the text I could read. | [V] for M1/M2 split; [I] for M3 |
| Firmware source | Fork loads firmware from a filesystem blob via `request_firmware`, not from iBoot memory. [I] Where that blob comes from on M3 is unknown. It would have to be extracted from macOS (in the ANE/AppleH15 driver or firmware bundle). Not the same mechanism as the GPU firmware flow, where m1n1 hands over data. | [V] ane_t6021_fwload.c; [I] M3 |
| Device tree | No upstream or Asahi `apple,t6030-ane` node found. M3 Pro devicetree is in linux-asahi 7.3 per the feature page, but ANE is TBA. | [V] feature page; [I] node absent |
| hollance/neural-engine | Community docs: ANE vs GPU, 16-bit behavior, unsupported layers, internals, reverse engineering. Mostly Core ML level, no H15 registers. | [V] https://github.com/hollance/neural-engine |
| maderix M4 | M4 (H16G): 16 cores, own DVFS, power-gated to 0 mW idle, MIL to E5 FlatBuffer, private `_ANEClient` APIs. Little on H13-H15. | [V] https://maderix.substack.com/p/inside-the-m4-apple-neural-engine |
| Black Hat Asia 2021 "ANE Internal" | Early M1 register/ISA-level material. | [V] listed at https://infocondb.org/con/black-hat/black-hat-asia-2021/apple-neural-engine-internal-from-ml-algorithm-to-hw-registers (not read in full) |

Not found anywhere: public H15 register map, public H15 firmware analysis, Asahi docs page "hw/soc/ane" content (fetch of the docs wiki returned only the index).

## 3. Compiler and model format problem

| Topic | Finding | Tag / source |
|---|---|---|
| Program format | Compiled "hwx" (Mach-O container with ANE microcode). Core ML recompiles a model to this each load, no cache seen by eiln. | [V] https://github.com/eiln/anecc |
| Open compile path | None truly open on Linux. anecc needs macOS Core ML (`tohwx`) to produce hwx, then runs it on Linux. tinygrad recovered the HWX format and the H11ANEInterface IOKit path years ago, but ANE support there is old, partial, not an LLM path. | [V] anecc README; arXiv ANE guide related-work; tinygrad search results (old READMEs only) |
| Newer macOS-side work | Orion (arXiv 2603.06728, 2026-03-06): bypasses Core ML via private `_ANEClient`/`_ANECompiler`, MIL to ANE, GPT-2 124M inference 170+ tok/s on M4 Max, training too. 20 documented MIL/ANE restrictions. All private macOS APIs, so not directly reusable on Linux. | [V] https://arxiv.org/abs/2603.06728 |
| Precision | FP16 math only (eiln). INT8 weights are dequantized to FP16 and on M1 give no bandwidth saving. LUT4 weights ran ~2.37x faster than FP16 on the unentitled path (M-series, paper). | [V] whisper PR; arXiv 2606.22283 |
| Shape / op limits | Static shapes, no ISA. Conv is the primary primitive, matmul as 1x1 conv is faster. Some ops (3D conv) never lower. Typical ANE LLM context 512 to 2048, some 4096. Weights are baked at compile time. | [V] whisper PR; maderix; arXiv ANE guide; insiderllm |
| Apple transformer recipe | (B,C,1,S) layout, Linear to Conv2d, single-head chunking. DistilBERT up to 10x faster, 14x less peak memory on iPhone 13. Published 2022-06-06. | [V] https://machinelearning.apple.com/research/neural-engine-transformers |

### Is the ANE good for LLM decode?

| Claim | Evidence | Tag |
|---|---|---|
| Decode is memory-bandwidth bound, GPU wins | ANEMLL decode on ANE vs MLX GPU (M4 Max): Llama 3.2 1B 47-62 vs ~204 tok/s; DeepSeek R1 8B ~9.3 vs ~50 tok/s. ANE ~2 W vs GPU ~20 W. | [V] https://insiderllm.com/guides/apple-neural-engine-llm-inference/ (2026-03-05, community numbers) |
| ANE suits encoders more than decoders | ANE guide chapter 14 verdict, as summarized from section headings. | [V] https://arxiv.org/html/2606.22283 |
| Prefill on ANE, decode elsewhere | Suggested hybrid by maderix. No Linux benchmark exists. | [V] maderix Part 2; [I] relevance to Linux |
| Dispatch cost | ~190 us per dispatch on M1 (0.23 ms floor), one command in flight. Hurts token-by-token decode. | [V] arXiv ANE guide |
| Peak | M1 Max ~12 FP16 TFLOP/s measured; M4 ~19 TFLOPS measured; ~32 MB SRAM on M4. | [V] arXiv; insiderllm |

Bottom line [I]: even with a perfect Linux ANE stack, expect small models (about 1B to 8B), short contexts, FP16 or LUT4 weights, and decode slower than the GPU. Value is low power, and possibly prefill offload.

## 5. Staged plan (private, personal use)

Prerequisite for everything: the ANE is only reachable once the kernel boots on T6030 with its power domains, DART and PMGR described in the devicetree. [I]

| Stage | Work | Effort estimate [I] | Risk |
|---|---|---|---|
| 0 | Confirm baseline: does your kernel contain `drivers/accel/ane`, is `apple,t6030-ane` anywhere (`git grep -i ane arch/arm64/boot/dts/apple/t603*`). Run llama.cpp CPU and, if GPU works, Vulkan. | 1 day | low |
| 1 | From macOS (same machine, dual boot): dump the ADT (`ioreg -p IODeviceTree`, or m1n1 `dump adt`) for the `ane` node: MMIO ranges, interrupts, power-domains, DART ids, `iommus`. Extract the H15 firmware blob from macOS (AppleH15ANEInterface / ANE firmware bundle). Check SHA and structure against the unencrypted-firmware description in the ANE guide. | 1 to 2 weeks | medium |
| 2 | Write a `t6030-ane` devicetree node (model on the T602x/T8112 one in `packaging/dt/t6021-ane.dts` in the fork). Power on via genpd only, no raw PMGR writes (the fork comments warn this can hang the SoC). | 1 to 3 weeks | **high**: bad register read can hang the SoC |
| 3 | Adapt `ane_t6021` boot path to H15: firmware load, RVBAR, mailbox, MBI handshake. Use m1n1 hypervisor tracing of macOS driving the ANE to learn the H15 mailbox and endpoint payloads. The M2 path's endpoint payloads are still "provisional" even in the fork. | 1 to 3 months | **highest unknown**: protocol and H15 differences are undocumented publicly |
| 4 | Run one trivial hwx (matmul, conv) produced on macOS with Core ML or the private compiler (Orion-style). Prove DART mapping and results. | 2 to 4 weeks | high |
| 5 | Userspace: reuse libane/anecc ideas, but H15 hwx layouts differ from H13. Build a graph-to-hwx path from macOS offline compile (static shapes, FP16, 1x1 conv matmuls). | 2 to 4 months | high |
| 6 | LLM integration: offline-compile fixed transformer blocks on macOS (ANEMLL-like), run prefill on ANE and decode on GPU or CPU. Expect small models, 512 to 2048 context. | 1 to 2 months | medium, and payoff likely limited |

Hardest unknowns: H15 firmware command protocol, per-dispatch overhead on Linux, hwx compatibility across macOS versions (compiled programs may break across macOS updates, per the ANE guide), and no GPU to cross-check since T6030 GPU is also unfinished. Total realistic effort: several months of part-time reverse engineering for a first matmul, more for LLM use. [I]

Practical shortcut [I]: do the GPU (Vulkan) bring-up first. It is more valuable for LLM speed on this machine.

### Asahi policy notes (brief)
- Asahi project bans contributions that use LLMs ("slop"): warning, then permanent ban. [V] https://asahilinux.org/slop (via search summary; the page itself did not fetch cleanly). Fine for private use, not for upstream submissions.
- Asahi reverse engineering follows clean-room style practice (hardware observed via m1n1 hypervisor, no Apple code copied). [I] general knowledge, not re-verified today. Do not paste Apple firmware or decompiled code into anything you plan to publish.
- Firmware blobs cannot be redistributed. [I]
