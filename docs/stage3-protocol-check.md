# Track B: is the ANE boot and handshake the same on H14 and H16, and what does that mean for H15 (T6030)?

Date 2026-10-27. Sources: public H14 driver copy (SiliconForest, `ane_t6021*`), public repo `iconidentify/omarchy-ane` (shallow clone, read only, nothing built or run), our own T6030 notes in `ane-linux/docs`. No Apple firmware or decompiled Apple code was copied anywhere. No ssh, no commit, nothing edited under the project.

Path shorthand used below:
- H14 = `drivers/accel/ane/` in a local copy of the SiliconForest kernel tree (files `ane_t6021.h`, `ane_t6021_boot.h`, `ane_t6021_boot.c`, `ane_t6021_fwload.c`)
- H16 = `ane/h16/` in `iconidentify/omarchy-ane` (`ane_h16_main.c`, `ane_h16_soc.c`, `ane_h16.h`) plus `receipts/2026-10-03-ane-h16/README.md`
- H15R = the same repo's own M3 notes, `receipts/2026-10-03-ane-h15/README.md` and `ane/h15/`
- F = `docs/t6021-ane-bringup-findings.md` in that repo

## Verdict: PARTLY

The H14 and H16 sources agree on the first half of the boot (release the ASC CPU, see the READY word 0x08042006 in SCRATCH7). They differ on where almost every register block sits, and they do not describe the same second half (what happens after READY). Also, nothing on the H16 side has ever run on silicon: it is a paper port from disassembled kext tables, calibrated against the H14 row. So "same on H14 and H16" really means "the H16 authors believe the first leg is the same".

For H15: the evidence we have points to the H14 register layout, not the H16 one. The boot path very likely shares the first leg. The second leg and the SCRATCH location on T6030 are unknown. A draft that tests only the first leg (power on, map the iBoot preload, release the CPU, wait for READY, stop) is justified and was written.

## What the H15 notes in the same repo add

- H15R says the M3 ADT (27.0) lists an ASC wrapper window at engine+0x1400000 (size 0x6c000) and an RVBAR window at engine+0x1050000, and DARTs at the H14 offsets. So on every register that the ADT lets us check, H15 follows H14, not H16 (`receipts/2026-10-03-ane-h15/README.md`, per-SoC table rows "ASC wrapper", "RVBAR block", "DART compatible and windows"). The mailbox at wrapper+0x8000 is inference there.
- That repo's H15 overlay adds four extra PMGR power nodes at +0xc000..+0xc018 for T6030 (`ane/h15/t6030-ane-experimental.dts`). Our own decode says those four are virtual with no register on T6030. Do not use that overlay. A genpd node on a non-existent word could stall or write a wrong register.
- H15R's own `ane_h15` module refuses to boot and says its boot path is "not built". So nobody has published a runnable H15 path; the repo has a gap here, not an answer.
- That repo's M3 ADT says `iop,ascwrap-v6` for macOS 27.0. Our installed macOS ADT says `ane,t8020` with six windows and no wrapper or RVBAR window. Different macOS generations describe the block differently. The firmware iBoot preloads comes from the stub OS (14.7 here), so the H15 image is an older generation than the 27.0 H16 one. If the T6021 history repeats (13.5 firmware: legacy SCRATCH/ring transport, no HELLO), the post-READY contract on a 14.7 stub is more likely the H14 legacy one than the H16 RTKit one. That is inference.

## What this means for H15 (T6030)

1. First leg (power on through ps_ane_sys, map the iBoot preload at 0x100_0000_0000, clear SCRATCH, release CPU 0 then 0x10, poll SCRATCH7 for 0x08042006): shared by H14 and H16 on paper, so likely shared by H15. This is what the draft tests.
2. Second leg (init struct publish, wake request, ChMan or RTKit): not shared and not derived for H15. The draft does not touch it.
3. Largest unknown: where the SCRATCH block sits on T6030. Candidate A is the H14 offset (+0x1840048). Candidate B is the H16 offset (+0x1880020), which is inside the H14 fatal range, so the draft never touches it. My estimate: about 65 percent A, 15 percent B, 20 percent something else. A read of the kext row for ane-type 0xc0 (AppleH11ANEInterface, `initializeANESoCConfig`) would settle it; the H16 authors decoded only the 0xa0, 0x100 and 0x110 rows.
4. Preload on a Linux boot: on T6021 iBoot does preload from the stub version, so likely (about 85 percent) also on T6030. But a no-map reservation for it does not exist in the running DT today (our Q2). The draft refuses unless the physical windows are covered by a DT no-map reservation, and unless RVBAR is already latched at 0x100_0000_0000.
5. DART and DAPF: the preload only runs if the ANE DARTs map it. That needs stage 2b (DART nodes enabled, `iommus` on the ane node). DAPF is not programmed by Linux on H14 either and H14 still boots, so this is probably not a blocker, but it is unmeasured on T6030.

Confidence: verdict PARTLY about 80 percent (the source comparison is solid; the H16 side is unproven). H15 shares the first leg about 65 percent. Chance that one reboot with the draft shows READY: roughly 20 to 30 percent (product of preload present, SCRATCH offset right, DART map sufficient, no missing PMU page or other pre-READY dependency). Chance it hangs the machine: low but not zero, mostly from a wrong SCRATCH offset. That is why the module reads first and its write path is gated.

## If the fast path fails: realistic time

- READY never arrives or the SCRATCH offset is wrong: decode the ane-type 0xc0 row in the kext on our own macOS (1 to 3 days of static work), then one more reboot test. Total about 1 week to a first handshake result.
- No iBoot preload on a Linux boot: Linux would have to stage the image itself. That needs the 14.7 stub image pinned and its patch-replay derived (iBoot's runtime patch words). For H14 this took weeks; for H16 the authors gave up on deriving it and copy from the preload. Count 2 to 4 weeks, with a real chance of needing a macOS 14.x trace.
- No static answer for the post-READY contract: trace macOS starting the ANE under the m1n1 hypervisor on T6030 (the kext starts the ASC lazily, only when CoreML opens it, so a kernel-only trace sees nothing: F sec. 8). H16 authors estimate 4 to 8 agent-days plus 2 to 6 tester runs just for the wake word, and the same again for commands. Count 1 to 3 months for a working command channel, matching our earlier Stage 3 estimate.

## Patch

Written: `trackB-h15-boot.patch` (new module `ane-linux/probe/ane_t6030_boot.c` plus one line in `ane-linux/probe/Kbuild`). `git apply --check` passes on a scratch copy of Kbuild. Compile check: clang `-fsyntax-only` against stub kernel headers only (not a real kernel build; the M3 is where the real build runs). The existing probe file and everything under the project are untouched.

Rules kept: genpd only (ps_ane_sys); the PMGR window is never mapped; every engine write needs `optin=t6030`, `engine_writes=1` and `handshake=1` (all default off); CPU_CONTROL and CPU_STATUS are read first and the CPU is never touched if RUN is set; every access passes `ane_off_ok()` (refuses +0x1854000..+0x1c28000 and +0x1010000); non-posted check on the DT chain; all waits bounded (poll at most 20 s); no IRQ requested; no firmware file read or named; after RUN nothing is unwound and the module stays pinned until reboot.

Open H15 assumptions inside it (all tagged "H15 ASSUMPTION" in the code): wrapper, CPU_CONTROL, CPU_STATUS and mailbox control offsets are the T602x values; SCRATCH0 at +0x1840048 (parameter `scratch0_off` to override); SCRATCH6 = 1 and the SCRATCH7 pulse are the H14 pre-release steps; iBoot latches RVBAR at 0x100_0000_0000 as on T6021; ANE DARTs use sid 0; TEXT and DATA sizes and IOVAs are the values from our T6030 ADT; the READY wait of up to 5 s is based on READY arriving about 4.2 s after probe on T6021 (the source does not say what that 4.2 s is measured from). Not done on purpose: P-1 tunables, the pre-CPU table, RVBAR writes, PMU page mapping, init publish, wake request, mailbox, RTKit.

How to use it to get a single-reboot test: one boot with the stage 2b DTB (DARTs enabled, iommus, no-map reservations at the addresses m1n1 shows for this boot), then `insmod ... peek=15` (reads only), look at the log, `rmmod`, then `insmod ... engine_writes=1 handshake=1 seg_text_pa=... seg_data_pa=...`. The read-only pass does not start the CPU, so no reboot is needed between the two.
